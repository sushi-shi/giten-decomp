# Script and equipment matching boundaries

These functions have reconstructed behavior but still need a source shape that
reproduces the retail instructions. Use `giten walls diagnose <rva> --asm` and
the matching loop for live scores; the observations below are retail control
flow and caller contracts, not score checkpoints.

| Function | Retail evidence | Remaining source question |
| --- | --- | --- |
| [PollEquipPart](../../src/Game/statuspanel.c) (`0x044fb0`) | Negative reset and held-click paths share the value-returning `returnPick` exit, preserving retail's four returns and 16 ordered relocations. The entire nonnegative-mode suffix matches retail byte-for-byte. Only the entry reset differs: current materializes the sentinel in DI and copies it to AX; retail sets EAX directly before storing AX. Current has five extra bytes and one extra instruction. The final reset remains a separate literal return after unhighlighting. | Recover the entry sentinel register without merging the negative reset into the final reset. Making only the negative reset return its literal again merges those paths and loses the retail four-return structure. |
| [RunEquipScreen](../../src/Game/statuspanel.c) (`0x042e60`) | Both objects have the same call, branch, return, and ordered-referent sequences. The opening key handling and both bag-count clamp bodies agree. After the second clamp, retail loads the equipment pick into `cx` and the two `ItemSlot`/count words into `edx` and `eax`; current MSVC uses `ax`, `ecx`, and `edx`. On the same-ammo finish path, current MSVC stores and reloads the 16-bit member argument through a stack home before the inlined finish call, while retail pushes its argument register directly. Grouping the two `ItemSlot` declarations is byte-identical and retained for clarity. Scoping `loaded` to the same-ammo arm changed the object but left the 98.45% match unchanged, so it was reverted. Naming the gun-removal pick as `EQUIP_PART_AMMO` made the whole object byte-identically clearer. The menu `part` and equip `count` are declared in their respective switch arms. The same-ammo quantity now comes directly from the typed `ItemSlot` returned by `GetRosterEquipSlot`, removing a one-use immutable aggregate local while preserving the complete normalized object byte-for-byte (SHA-256 `8677c9726c6c8a6031272233f5b7438d8e1cc0c079a03a809dcef7d48d48fa8b`). Per-unit comparison still reports 98.45%; current has 490 instructions versus retail's 484, while both retain 68 calls, 28 branches, 11 returns, and 139 relocations. A raw COFF comparison against the prior object differs only in five ASCII digits of `$L` local label names; code and relocation bytes are identical. The earlier non-const `loaded` scope probe changed the object, whereas const initialization and the direct quantity expression compile identically. Splitting the shared `slot` into separate equip, preview-remove, and remove-arm locals lowers similarity to 95.47%, so the single aggregate local remains. Making `FinishEquipChange` a `void` inline helper and returning `STATUS_COMMAND_NONE` at its three call sites keeps the complete normalized `statuspanel` object byte-identical (SHA-256 `8677c9726c6c8a6031272233f5b7438d8e1cc0c079a03a809dcef7d48d48fa8b`); the helper performs the common state change while the caller owns its status result. A comma-expression macro for that helper lowered the match to 98.20%. Making the helper read `g_statusMember` directly instead of accepting the live value as an argument also fell to 98.20%, so the explicit argument remains. A `const i16` snapshot of `g_statusMember` in the same-ammo arm lowered the match to 97.11% and was removed; the existing global reload preserves its live value after `TakeBagItems`. A `const i16 pick` snapshot immediately before `EquipItem` preserved the 98.45% score and the 490-instruction/68-call/28-branch/11-return/139-relocation structure but changed the normalized object without correcting the load order; it added only a one-use local and was removed. | Trace the aggregate copy and argument lifetime from the bag/equipment producers before changing the source order or storage model. The declaration and definition now type this input as `EquipPickMode` while retaining its `i16` storage and signed threshold checks. A/B per-unit compiles leave the complete normalized `statuspanel.obj` byte-identical (SHA-256 `03c965ce7c23e217636e86eab514473ad154669cb5ab40712cc3d80c78dc8bc1`), with the 93.97% shared-return wall unchanged. The computed row remains `i16` until its bounds check; treating it as an `EquipPart` before that check would assert an unproven value range. |
