# Script and equipment matching boundaries

These functions have reconstructed behavior but still need a source shape that
reproduces the retail instructions. Use `giten walls diagnose <rva> --asm` and
the matching loop for live scores; the observations below are retail control
flow and caller contracts, not score checkpoints.

| Function | Retail evidence | Remaining source question |
| --- | --- | --- |
| [PollEquipPart](../../src/Game/statuspanel.c) (`0x044fb0`) | A negative mode sets all of `eax` to `-1`, stores `ax` into the selected-part word, and returns directly before loading `member`; the final reset stores an immediate `-1` and sets only `ax` before its return. Mode 100 enters the final unhighlight/reset path. Invalid coordinates, an excluded part, and an active curse converge on that path. Selecting the already highlighted part returns without resetting it. Retail has 130 instructions, five calls, 19 branches, four returns, and 16 relocations; current has 123 instructions, five calls, 19 branches, three returns, and 15 relocations. | MSVC merges the negative-mode reset with the final reset. The `else if` mode dispatch is byte-identical and retained for clarity. Scoping the coordinate locals to the polling arm and the read-only part local to its valid-row arm compiled byte-identically and is retained. Inverting the outer guard, returning the stored global, returning the assignment from either or both reset sites, initializing the part local to the sentinel, putting the early reset in an inline helper, and using `part` as the early result carrier all compiled to the same object and were reverted. A scoped `cleared` result also retained three returns and 93.97%; widening that scoped reset result to `i32` still retained three returns and 93.97%, so both were reverted. Naming `mode < EQUIP_PICK_PART` as a `const b16` reset predicate lowered similarity to 92.78% and still did not recover the separate return, so the direct signed comparison remains. Recover a source-level boundary that retains the entry store through `ax` and direct return for every negative mode. Callers pass `EQUIP_PICK_RESET`, `EQUIP_PICK_PART`, `EQUIP_PICK_ATTACH_TARGET`, or `EQUIP_PICK_CLEAR`; the retail signed comparison also defines behavior for other negative values. |
| [ItemListMenuHandler](../../src/Game/statestack.c) (`0x01a240`) | The callback accepts `MENU_EVENT_DESTROY`, `MENU_EVENT_BEGIN_PAGE`, and `MENU_EVENT_ADD_ROW` from `SetMenuItems`. The swap persists through the final line writer and destroy arm. The retail row arm rereads the entry item after calls; the shared `GetItemListItem` accessor now names that repeated per-use read at all 12 sites in three translation units. Those three compiled objects are byte-identical to their pre-helper versions, leaving the prologue register swap as the first difference. Scoping `record` and `modes` to the row event and making the read-only record pointer `const` preserves the full normalized `statestack` object (`6046db0973a8c3693eb33f69ac0b5c4de7edbec34f20b4a572826fdf41925ccd`). Moving their initialization into a nested block after the special-item early return also preserves the complete current normalized object (`5f33fa9a38a34af5b42c5ebd8b7daffc63f92f79a1a2f19e9aee8b1d91351299`) and is retained to name their actual lifetime; MSVC C rejects declarations at first use without that block. The callback's shared list pointer is now a constant pointer snapshot, preserving the complete normalized `statestack.obj` byte-for-byte (SHA-256 `97953e2a451f8d33e0b7601dd4a2cdda162a23d5116ca07a61784d9740956f98`). Narrowing `AddItemUseMenuLine` to the plane handle changed object bytes without improving 96.28%, so it was reverted. Reading `menu->items.itemList` separately in row and destroy arms added three instructions and lowered the match to 90.51%, so its shared entry snapshot remains. | No missing event arm is indicated. A justified local or helper boundary would need to explain both pointer lifetimes; declaration and case-scope changes alone did not. Avoid caching the item across calls without evidence that those calls cannot change it. |
| [RunEquipScreen](../../src/Game/statuspanel.c) (`0x042e60`) | Both objects have the same call, branch, return, and ordered-referent sequences. The opening key handling and both bag-count clamp bodies agree. After the second clamp, retail loads the equipment pick into `cx` and the two `ItemSlot`/count words into `edx` and `eax`; current MSVC uses `ax`, `ecx`, and `edx`. On the same-ammo finish path, current MSVC stores and reloads the 16-bit member argument through a stack home before the inlined finish call, while retail pushes its argument register directly. Grouping the two `ItemSlot` declarations is byte-identical and retained for clarity. Scoping `loaded` to the same-ammo arm changed the object but left the 98.45% match unchanged, so it was reverted. Naming the gun-removal pick as `EQUIP_PART_AMMO` made the whole object byte-identically clearer. The menu `part` and equip `count` are declared in their respective switch arms. The same-ammo quantity now comes directly from the typed `ItemSlot` returned by `GetRosterEquipSlot`, removing a one-use immutable aggregate local while preserving the complete normalized object byte-for-byte (SHA-256 `8677c9726c6c8a6031272233f5b7438d8e1cc0c079a03a809dcef7d48d48fa8b`). Per-unit comparison still reports 98.45%; current has 490 instructions versus retail's 484, while both retain 68 calls, 28 branches, 11 returns, and 139 relocations. A raw COFF comparison against the prior object differs only in five ASCII digits of `$L` local label names; code and relocation bytes are identical. The earlier non-const `loaded` scope probe changed the object, whereas const initialization and the direct quantity expression compile identically. Splitting the shared `slot` into separate equip, preview-remove, and remove-arm locals lowers similarity to 95.47%, so the single aggregate local remains. Making `FinishEquipChange` a `void` inline helper and returning `STATUS_COMMAND_NONE` at its three call sites keeps the complete normalized `statuspanel` object byte-identical (SHA-256 `8677c9726c6c8a6031272233f5b7438d8e1cc0c079a03a809dcef7d48d48fa8b`); the helper performs the common state change while the caller owns its status result. A comma-expression macro for that helper lowered the match to 98.20%. A `const i16` snapshot of `g_statusMember` in the same-ammo arm lowered the match to 97.11% and was removed; the existing global reload preserves its live value after `TakeBagItems`. A `const i16 pick` snapshot immediately before `EquipItem` preserved the 98.45% score and the 490-instruction/68-call/28-branch/11-return/139-relocation structure but changed the normalized object without correcting the load order; it added only a one-use local and was removed. | Trace the aggregate copy and argument lifetime from the bag/equipment producers before changing the source order or storage model. The declaration and definition now type this input as `EquipPickMode` while retaining its `i16` storage and signed threshold checks. A/B per-unit compiles leave the complete normalized `statuspanel.obj` byte-identical (SHA-256 `03c965ce7c23e217636e86eab514473ad154669cb5ab40712cc3d80c78dc8bc1`), with the 93.97% shared-return wall unchanged. The computed row remains `i16` until its bounds check; treating it as an `EquipPart` before that check would assert an unproven value range. |
